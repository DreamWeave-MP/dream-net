# Audit of netcode's bundled libsodium

netcode does not link a system libsodium. It ships an amalgamated subset of libsodium as two
files, `sodium/sodium.c` and `sodium/sodium.h`, generated by netcode's authors and committed to
the netcode repository. dream-net vendors those two files byte for byte at the netcode
pin (`vendor/PROVENANCE.toml`); it does not fetch libsodium itself.

This audit was made on 2026-11-18 against netcode v1.4.10
(`d6bc96dafe2cc6c9b77903db7ce86f832a2de996`) and a full clone of
https://github.com/jedisct1/libsodium (tags 1.0.15 through 1.0.22 and `master` at `7614ada6`).

`sodium/` is byte-identical between netcode v1.4.9 and v1.4.10 (`git diff v1.4.9 v1.4.10 --
sodium/` is empty), so this audit holds for both.

## Method

`sodium.c` and `sodium.h` are concatenations of libsodium files, each introduced by a
`/* ================= sodium_<file> ================= */` marker; the ChaCha20 `u*.h` kernels and
the Poly1305 `donna32/64.h` kernels are inlined where upstream `#include`s them. Every section
was mapped to its libsodium source file (the implementation-body headers were expanded in the
upstream copy the same way), blank lines and `#include "..."` lines were dropped on both sides,
and the remainder was diffed line by line against each libsodium release from 1.0.15 to 1.0.22
and against `master`. The release whose text differs least is the section's origin; the
remaining differences were read one by one.

## Which libsodium it is

The tree is not a single libsodium release. netcode's `sodium/NOTES.md` says the crypto
"tracks libsodium 1.0.22"; that holds for the crypto, not for the support code:

| Sections | Closest release | Remaining differences |
| --- | --- | --- |
| `aead_chacha20poly1305.c`, `aead_xchacha20poly1305.c` | 1.0.21 (identical) / 1.0.22 | 1.0.22 adds only `/* LCOV_EXCL_LINE */` comments; xchacha has a `#define _pad0 _pad0__x` rename bracket |
| `verify.c` | 1.0.21 / 1.0.22 | adds `#pragma GCC target("sse2")` under `__GNUC__` (Clang ignores it; see below) |
| `stream_chacha20.c`, `chacha20-ref.c`, `core_hchacha20.c`, `onetimeauth_poly1305.c` | 1.0.22 | amalgamation renames and `#undef`s, `NETCODE_CRYPTO_LOGS` printfs (off unless defined), LCOV comments dropped; `onetimeauth` returns right after picking SSE2 (same result) |
| `dolbeau_chacha20-ssse3.c`, `dolbeau_chacha20-avx2.c` | 1.0.20 through 1.0.22 (identical) | amalgamation renames, `#undef`s, a `*_link_warning_dummy` int |
| `poly1305-sse2.c` | 1.0.21 / 1.0.22 | comment whitespace, amalgamation renames, a `*_link_warning_dummy` int; carries the 1.0.22 `optblocker_u64` final reduction |

So: **crypto text at libsodium 1.0.21/1.0.22, support code at libsodium 1.0.17**
(`b732443c442239c2e0184820e9b23cca0de0828c`), plus netcode's local edits listed above.
`SODIUM_VERSION_STRING` says `1.0.22`. No section is a mixture of releases inside itself.

No file was modified in a way that changes cryptographic output: the AEAD, stream, Poly1305 and
verify text is upstream's apart from renames that the amalgamation needs. netcode's own
known-answer test (`test_crypto_aead_vectors`, first in `netcode_test()`) pins the ciphertext
and tags of both AEADs, and it passes in our build (`tests/native_build_upstream.rs`).

## What is in it

Primitives netcode calls (from the production part of `netcode.c`):

- `crypto_aead_chacha20poly1305_ietf_encrypt` / `_decrypt` (packets),
- `crypto_aead_xchacha20poly1305_ietf_encrypt` / `_decrypt` (connect tokens, challenge tokens),
- `randombytes_buf` (keys, nonces, `netcode_random_bytes`),
- `sodium_init` (from `netcode_init`), `sodium_memzero` (28 call sites: key and token wipes).

Their support: ChaCha20 (ref, SSSE3, AVX2), HChaCha20, Poly1305 (donna32/donna64, SSE2),
`crypto_verify_16/32/64`, CPU feature detection, randombytes with the `sysrandom` backend,
`sodium_malloc` and friends (present, unused by netcode).

**Language.** C only. No assembly files; the `amd64`/`avx` assembly paths are compiled out
(`HAVE_AMD64_ASM`, `HAVE_AVX_ASM` are never defined). Inline asm appears only as an empty
optimisation barrier (`__asm__ __volatile__("" ...)` in `crypto_verify_n` and the SSE2 Poly1305
reduction) and in x86 `cpuid`/`xgetbv` feature detection.

**CPU dispatch.** `sodium_init` runs `cpuid` (x86) and picks ChaCha20 AVX2 > SSSE3 > reference
and Poly1305 SSE2 > donna at run time. The SIMD functions enable their instruction sets per
function (`#pragma clang attribute push(... target(...))`), so no global `-m` flags are needed and
the same objects run on any x86-64. On aarch64 and anything else, the portable reference and
donna64 code is used (libsodium has no NEON ChaCha20/Poly1305 either). The one GCC-only pragma,
`#pragma GCC target("sse2")` in `verify.c`, is ignored by Clang with `-Wunknown-pragmas`; it guards
code compiled only when `__SSE2__` is already defined (x86-64 baseline), so ignoring it changes
nothing.

**Randomness.** `randombytes_buf` uses the `sysrandom` backend:

| Platform | Source |
| --- | --- |
| Linux | `getrandom(2)` through `syscall(SYS_getrandom, ..., 0)` in chunks of at most 256 bytes, blocking until the kernel pool is initialised; if the syscall is unavailable, `/dev/urandom` after one `poll` on `/dev/random` |
| FreeBSD 12+ | `getrandom` |
| macOS, other Unix | `/dev/urandom` (falls back to `/dev/random`), opened once with `FD_CLOEXEC`, read with `EINTR` retry |
| OpenBSD | `arc4random_buf` |
| Windows | `RtlGenRandom` (`SystemFunction036`, `advapi32`) |
| PlayStation (`__ORBIS__`, `__PROSPERO__`) | stubs that write nothing (documented in NOTES.md; not a dream-net target) |

Any read failure calls `sodium_misuse()`, which aborts: no key is ever made from an unfilled
buffer on the supported platforms.

**`sodium_init` and threads.** `sodium_init` is guarded by `sodium_crit_enter`/`leave`. In this
amalgamation those are a real lock only on Windows (a `CRITICAL_SECTION`). On every other
platform neither `HAVE_PTHREAD` nor `HAVE_ATOMIC_OPS` is defined (there is no autoconf), so the
lock is a no-op and `sodium_init` is **not thread-safe**; neither is `netcode_init`, whose
reference count is a plain `int`. dream-net does not define either macro (that would be a
configuration netcode has never tested); instead the binding layer must serialise
`netcode_init`/`netcode_term` itself (see `BUILD.md`, "Initialisation"). After `sodium_init` has
returned, `randombytes_buf` and the AEADs are reentrant.

**Windows lock lifetime.** netcode's own roadmap (main after v1.4.10) records that the
`CRITICAL_SECTION` above is never deleted, which trips Application Verifier when a DLL that
statically contains it unloads. Low severity, Windows-only, unfixed upstream at the pin.

**`sodium_memzero`.** With no `HAVE_MEMSET_S`, `HAVE_EXPLICIT_BZERO`, `HAVE_EXPLICIT_MEMSET` or
`HAVE_WEAK_SYMBOLS`, it is libsodium's volatile-pointer byte loop on every non-Windows platform
and `SecureZeroMemory` on Windows. Volatile stores survive optimisation, including cross-language
LTO.

Every file is under libsodium's ISC license (Frank Denis, 2013-2026), whose text heads both

LGPL, AGPL, MBSL or non-commercial terms. See `LICENSES.md` and `NOTICE.md`.

## Vendored versus system libsodium

**Vendored bundle chosen.** A system libsodium was considered and rejected:

- it breaks the hard requirement that the packaged crate builds offline and reproducibly with
  nothing but a Clang toolchain (pkg-config, a package manager, and whatever version the host
  happens to have);
- netcode's wire format depends on the exact AEAD constructions, and a host libsodium would bring
  a different version per machine, untested against netcode's vectors;
- symbol privacy (one `dn_native_` prefix, `BUILD.md`) is impossible for a shared system library,
  so a host that links its own libsodium could collide with ours.

The cost is that security fixes in libsodium reach us only through a netcode pin move or a local
patch. Hence the review below.

## Libsodium changes since the bundled code

Changes in libsodium between the bundled versions and 1.0.22 (and `master` on 2026-11-18) that
touch what netcode uses:

- **AEAD, ChaCha20, Poly1305, verify.** The 1.0.21/1.0.22 hardening (an acquire fence between
  tag verification and decryption in all AEAD decrypt paths; the `optblocker` barriers in
  `crypto_verify_n` and in the SSE2 Poly1305 final reduction) is present. 1.0.22 to `master`
  changes only coverage comments in these files. Nothing missing.
- **randombytes.** 1.0.17 to 1.0.22: `getrandom()` through libc's wrapper when autoconf finds it
  (the bundled code uses the raw syscall: same kernel call), DragonFly BSD support, WASI and
  Cloudflare Workers paths, a `const` on `randombytes_set_implementation`. None is a security fix
  for Linux, macOS or Windows.
- **utils.** `sodium_memzero` gained `memset_explicit` (C23) and a Windows fallback when
  `SecureZeroMemory` is unavailable; `sodium_compare` casts its operands; neither changes what
  this build compiles to on supported platforms (`sodium_compare` is unused).
- **core.** `_sodium_crit_init` became `static` (1.0.19). Here it is external on Windows; the
  `dn_native_` prefix keeps it from colliding.
- **runtime.** aarch64 and Android crypto-extension detection for AES (unused by this subset).

**Refreshing the support files is not warranted** for security: no change since 1.0.17 in them
fixes a vulnerability reachable through netcode's calls on the supported platforms. Mixing in
newer support files by hand would also create a third, untested combination. If it is ever
wanted, it belongs upstream in netcode (which regenerates the amalgamation and re-runs its
vectors), followed by a pin move here, not a local patch.

## Open items

- The non-thread-safe `sodium_init`/`netcode_init` on non-Windows platforms (above) is a binding
  requirement, not a defect we patch.
- The Windows `CRITICAL_SECTION` lifetime defect is upstream's to fix (roadmap item
  `sodium-lock-dll-unload`).
- This audit compared text, not compiled output. Byte-identical AEAD output to stock libsodium is
  asserted by netcode's known-answer vectors, which we run, not by an independent comparison.
